# F/G 生产关系数据库选型：MySQL

状态：已确认的目标架构；实施未完成。日期：2026-11-16。

## 决策与边界

F/G生产关系数据库由PostgreSQL目标调整为MySQL，与A—E技术选型统一。使用InnoDB；具体MySQL版本、字符集、排序规则、时区、备份和高可用基线与A—E共同冻结，不把MariaDB视为已经验证的兼容替代。

一个统一前端、F/G Go后端、A—E Python后端的划分保持。前后端及F/G—A—E HTTP接口、参数、权限与数据权威不变。MySQL不替代图数据库、向量存储或其他专业组件。

双方可共用受控MySQL基础设施，但分别使用逻辑库和最小权限账号。建议库名application_platform与cognition_platform，均为目标名称。Go与Python不得共同迁移同一业务表或跨服务直读直写对方表；跨域业务通过现有契约交互，不假设跨库业务事务自动原子提交。

## 当前代码事实

当前验证宿主仍支持JSON、SQLite、PostgreSQL JSONB聚合状态。MySQL驱动已在上游Go依赖中，但F/G尚未提供OpenMySQL、--storage mysql、MySQL迁移与真实数据库CI。现有PostgreSQL测试记录保持历史事实，不改写成MySQL已验证。运行命令和现有CI此时不变。

PostgreSQL不再是F/G生产目标。现有适配可暂留回归与显式数据导出，不继续作为新增生产能力的首选基础。不得把单行JSONB改成MySQL JSON后宣布生产化完成；最终应采用规范业务表、索引与明确事务边界。

## 目标数据与工程位置

| 数据域 | 表设计职责 |
| --- | --- |
| 应用与发布 | 应用、草稿版本、不可变发布快照、发布指针、发布检查 |
| 对话运行 | 应用会话绑定、消息、Turn与实际资源使用引用 |
| 权限 | 主体关联、资源授权、版本和撤销记录；企业身份仍由正式身份源负责 |
| 治理 | 审计、事件去重、基础用量、异常版本与状态、隔离的公共/个人配置 |
| 可靠投递 | 本地业务与待发送事件同事务；发送方发件箱按跨服务职责分别实现 |

沿用backend/platform及internal/platform的功能命名；MySQL适配位于相应持久化实现，正式迁移放在backend/platform/migrations中按现有框架登记。上述表为设计范围，具体表名/字段和仓储接口需另行设计，不宣称已存在。应用配置、发布快照等可保留JSON字段；可筛选字段与关联键不可全部隐藏在整库JSON中。

生产查询应在数据库按tenant_id及权限条件过滤、分页，并建立对应索引。标识符比较、复合唯一键、幂等键和版本号的大小写语义必须明确；数量/金额使用明确精度，时间统一UTC，审计与业务修改同事务。

## 实施顺序

1. 与A—E冻结MySQL部署基线、逻辑库/账号及迁移所有权。
2. 增加MySQL连接、配置、超时、就绪检查和专用CI测试库；已有运行模式继续可用。
3. 设计正式关系表、租户索引、唯一约束与升级迁移，分步替换当前Store聚合读改写接口，维持现有版本/授权/审计事务语义。
4. 在真实MySQL验证并发保存/重命名、撤权可见性、发布指针、事件去重、事务回滚/取消与重启回放。
5. 提供显式数据迁移与核对、备份恢复和回滚方案；不自动迁移、删除原JSON/SQLite/PostgreSQL数据，不向生产库自动播种Mock数据。

MySQL迁移需单独处理DDL提交行为、初始化竞争、锁等待和死锁。不可照搬PostgreSQL advisory lock、JSONB强转、ON CONFLICT或RLS假设。有界重试只重做可确认安全的本地事务，不重发未知状态的模型/业务执行。

## 验收门槛

- 必须有真实MySQL测试，缺少测试库配置不能静默跳过必选CI。
- 原69项Go测试与最新前端测试/契约/浏览器回归持续通过；另补MySQL专属兼容、并发与迁移测试。
- 证明租户/用户隔离、同版本并发只有一个成功、无变化不重复审计、幂等事件不重复入账。
- 编译程序MySQL模式完成启动、业务调用、退出/重启、已完成结果回放，且回放不重复执行或计费。
- 生产切换前完成容量、负载、备份恢复、升级/回滚演练；MySQL适配通过不等于SSO、多节点或真实A—E联调完成。

## 实施进展：MySQL过渡适配

2026-11-16：已增加OpenMySQL、--storage mysql、环境变量DSN及独立MySQL 8.4 CI服务。适配保留现有聚合Store接口，以InnoDB行锁保护状态更新，不是正式表迁移；上文“尚未提供MySQL运行模式”是决策时基线，以本节为最新状态。正式关系表、仓储接口拆分、生产迁移与数据迁移仍未完成。真实数据库执行状态以对应PR CI为准。

初始化安全补充：过渡适配在种子写入前检查实际引擎/字段/主键及异常状态行；不兼容表拒绝启动，由显式迁移处理，不自动ALTER或清理数据。六宿主并发初始化、原数据保护和失败回滚纳入真实MySQL CI。检查不等于规范生产表或正式迁移工具完成。

审计拆表第一步：通过显式迁移将v1审计移入cognara_fg_audit并切换schema_version=2，状态和审计变更同事务。其他域仍为聚合JSON，未取消全局状态锁，数据库侧权限分页仍待演进。v2需完整备份状态和审计表，原v1快照工具会拒绝v2，不提供自动回滚。迁移要求先在副本验证并保留完整迁移前库；说明见第二十轮测试记录。

业务审计增量追加：MySQL v2普通API使用Operational存储入口，状态读取省略审计历史，修改仅处理本次新事件，按索引尾序号追加并与业务状态同事务提交。完整Read/Update仍保留核对语义；新业务回调不得读取Audit历史。全局状态锁、其他域聚合JSON和整体序列化仍待演进，未宣称完成无锁生产存储。

v2恢复能力补齐：当前快照工具已支持同一只读事务导出业务状态与关系审计，使用显式版本及摘要恢复到没有状态/审计记录的独立库，两部分同事务提交，未知JSON字段保留。替代前文“现有工具仅支持v1”的限制，旧版工具仍拒绝v2。该逻辑快照不替代完整物理备份和外部证据恢复；全局状态锁及其他业务表拆分仍未完成。

迁移预检查：当前cognara-migrate-audit支持互斥的--check/--apply。前者只读检查v1迁移条件或流式验证v2审计，输出机器可读报告，不初始化/播种/修改数据库；后者始终重新校验。预检查不是备份、锁定或成功承诺，其他业务表与全局锁改造仍未完成。

审计表基线补充：新表显式utf8mb4，三个文本投影列必须支持utf8mb4；身份键仍按完整VARBINARY比较。结构校验拒绝前缀、表达式或不可见索引，要求既有BTREE列/唯一性定义。不兼容表须先由运维显式升级，不自动ALTER，MySQL 8.4真实回归覆盖latin1默认库中的迁移与恢复。

配置写入仓储过渡：MySQL v2已开始用单配置投影+JSON_SET事务保存个人/公共配置，避免将全部应用/会话状态传回Go重新序列化，审计仍同事务追加。保留旧版本/其他适配及别名回退；仍有状态行FOR UPDATE锁，尚未实现配置关系表或全局数据库锁拆分，不应据此声称生产数据层完成。
