# 第四十二轮：异常处理与请求审计追溯（2026-11-17）

PR #38 已合并 main：4f49f9415c3062c5e64865d3a0d92425965dea82。继续复用 Cognara/TDesign、既有异常状态 API、审计查询及原错误观测记录。

## 实现

- 异常行与详情提供关联审计入口，以固定前端路由和经过格式校验的请求标识建立链接；审计页初始化通用query筛选。不新增后端参数，不改变管理员和租户权限检查。
- 确认、解决和重新打开使用固定异常/版本/目标状态的受控确认框。输入源、视图和迟到响应不能切换已提交目标。
- 序列化提交，校验成功响应的标识、版本、目标状态和原请求关联；冲突、权限变化、未知结果均要求重新加载核对。重新加载失败或仍在途不解除阻断。
- 状态处理只更新处理记录，不重试模型或业务服务；保留服务端CAS和合法状态机。

## 回归

新增7项前端测试：合法迁移、快照/版本/请求绑定、重复与晚响应、不确定结果/失配响应、关闭/重载，以及审计链接的固定路由和非法/多值/超长输入。

新增2项Go HTTP测试：未配置模型测试的真实503生成异常和请求审计；确认/解决/重开、旧版本409、普通用户403、不重复模型测试/不计新用量或会话；同请求标识的外租户记录不进入追溯，外租户异常不可修改。

Chromium：通过Node向本地Go开发宿主发起一次预期的未配置模型测试503，不调用外部提供方；读取实际异常，在UI由详情跳转关联审计、核对URL和筛选，再执行确认/解决/重开并检查每次携带的新版本及原请求关联。预期503不作为浏览器控制台错误吞掉；浏览器监听仍保留非预期错误检查。
