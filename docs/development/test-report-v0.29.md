# 第二十九轮：MySQL恢复后扩展字段保留

基线：PR #25已合并main，a08aa98a0da3f84d39f9ec0ae485bc516e7013a0。

## 问题与实现

现有导出/导入可以保留未知JSON字段，但普通业务写入将State重新序列化，导致不在当前Go结构中的顶层字段在恢复后第一次写入时被静默丢弃。此次在已有行锁和事务内同时取得该行原始JSON，将未知顶层字段合入本次新状态；不用启动时缓存、不额外查询、不改变事务或审计原子性。适用于MySQL v1和v2、完整Update及Operational写入。

已知State字段完全使用业务回调产生的新值，包括删除与nil；旧大小写别名不保留，避免下次Go解码读取陈旧状态。不对未知字段按大小写合并，例如future与Future均原样保留。使用RawMessage保留大整数、null及未知根对象内部的完整值，不经float64转换。MySQL自身JSON排序/空白规范化仍存在，不承诺文件字节完全相同。

## 验证

新增3项顶层Go测试（总计103项）：

- 纯合并：未知对象/大整数/null、未知键大小写区分、已知字段删除及旧别名清除、非法输入拒绝。
- 真实v1/v2快照导出→空库恢复→Operational/完整业务写入→失败回滚→再次导出，检查扩展不丢失、已删除配置不复活、审计追加与重复审计回滚；v2关系审计仍不重新写入历史。
- 两个已启动Store并发更新，在它们启动后注入的最新顶层扩展仍被保留，两次业务更新均可见，证明不是从陈旧内存保留数据。

本地存储/API包测试通过，真实数据库本地未配置时跳过；正式MySQL验证以PR最新完整CI为准。CI继续执行竞态检测、真实MySQL/PostgreSQL、接口契约、恢复/迁移命令验收、57项前端测试和浏览器回归。

## 边界

仅作用于MySQL持久化的未知顶层字段及其内部值；不保留已知业务对象/数组内部的未知属性，不使旧代码理解未来字段，不承诺任意新版本的双向兼容。PostgreSQL/SQLite/JSON写入行为未扩展。没有数据库schema、HTTP参数或UI变更；业务关系表拆分、全局锁改造、生产负载与真实A–E联调仍待完成。
