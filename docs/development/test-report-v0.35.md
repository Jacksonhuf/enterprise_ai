# 第三十五轮：MySQL异常列表定向分批读取

基线：PR #31已合并main，80d60e7ddf31b6a600390dd1ea94881f70b2a6b5。部署方案不变。

## 实现

MySQL v2异常列表在ReadOnly/RepeatableRead事务中通过JSON_TABLE按完整字符串tenant_id筛选，按数组接收序号倒序分批投影，仅返回当前企业候选，不读取整个body到Go。每批最多200条，Go应用原query/status/time过滤并取limit+1判断是否有下一页。无Store.mu和FOR UPDATE；请求取消与5秒超时生效。

沿用v1游标和原fingerprint，继续使用event_id→grant_id→id的稳定标识优先级。每次从当前快照重新寻找第一个仍匹配筛选的游标锚点；找不到返回既有400刷新提示。新追加记录不挤入旧锚点之后的页面，状态变化导致锚点离开筛选时拒绝继续；不将旧授权或筛选结果缓存。仍按原规则处理缺少稳定标识的分页边界。

v1、其他存储及相关audit/exceptions顶层大小写别名回退原路径。查询失败返回错误，不将数据库不可用当空列表；无HTTP参数、schema_version或表结构变更。返回投影JSON保持未知值精度，筛选仍使用原Go字符串/时间规则。

## 验证

新增3项顶层Go测试，总计122项：

- 同时持有Store本地互斥锁和数据库未提交写锁，读取仍返回已提交快照、过滤外国/数字/尾空格企业标识，保留未知大整数；body不变、失效锚点/取消拒绝及v1/别名回退。
- 450条本企业记录及穿插外企记录，逐页比较v1/v2数据和游标。覆盖超过200候选的批次、稀疏搜索、中文搜索、状态、纳秒精度、小写时间、0001年、无结果及优先event_id游标；迁移前游标在新路径可继续使用。
- 真实HTTP追加后旧页稳定、普通用户/外企用户403、换筛选/坏游标/非法参数400、状态变更使锚点失效400、数据库不可用503。

本地存储/API包测试已通过。缺少MySQL配置时本地数据库用例跳过，真实数据库结论以最新完整CI为准。继续回归竞态检测、MySQL/PostgreSQL、接口契约、运行/恢复/迁移、57项前端与浏览器业务流程。

## 边界

数据库仍扫描JSON数组，后续页仍需在当前快照中定位旧ID锚点；此项不宣称租户索引、恒定成本分页、独立异常关系表或吞吐基准。逐步拆分领域仓储后，仍需正式关系表、写锁拆分和生产联调。
